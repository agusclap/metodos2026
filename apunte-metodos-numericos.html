Capítulo 1 — Localización de raíces

Bisección método cerrado

Parte de un intervalo [a,b] donde f(a)·f(b) < 0 (cambio de signo → por Bolzano hay una raíz adentro). En cada paso se calcula el punto medio y se descarta la mitad del intervalo que no cambia de signo.

Pseudocódigo
hacer:
    c = (a + b) / 2
    si f(c) == 0 → raíz exacta, listo
    si f(a)·f(c) < 0 → b = c
    si no        → a = c
mientras (error > tolerancia) Y (iter < max_iter)

Ejemplo paso a paso: primera iteración a mano

f(x) = (x+1)/(x+4) − 0.25x, intervalo [a,b]=[1.75, 3.2] (acá c_viejo arranca en b, no en a — así lo pedía este enunciado puntual, revisar siempre qué pide el criterio de error de cada ejercicio). 

c = (a+b)/2 = (1.75+3.2)/2 = 2.4750000000

f(a) = f(1.75)  =  0.0407608696
f(c) = f(2.475) = -0.0820704633
f(a)·f(c) < 0   →   la raíz está entre a y c   →   b = c

error = |c − c_viejo| / (½·|c + c_viejo|) × 100        (c_viejo = b = 3.2)
      = |2.475 − 3.2| / (½·|2.475 + 3.2|) × 100
      = 0.725 / 2.8375 × 100
      = 25.5506607930 %

Nuevo intervalo: [1.75, 2.475]

Cuántas iteraciones hacen falta (Problema 4)

Cada bisección acota el error con |r − c| ≤ (b−a)/2 sobre el intervalo vigente. Como el intervalo se parte a la mitad en cada paso, después de n bisecciones sucesivas:

|r − cn| ≤ b − a2n

Pidiendo que ese error sea menor que un δ elegido y despejando n:

n = ⌈ log2( (b−a) / δ ) ⌉  = ⌈ ln((b−a)/δ)ln 2 ⌉

Se redondea siempre hacia arriba (ceiling), porque n tiene que ser entero y la desigualdad se tiene que seguir cumpliendo.

Verificado con datos reales

[0,1], δ=1e-4 → n=⌈13.29⌉=14 iteraciones. [60,65], δ=1e-5 → n=⌈18.93⌉=19 iteraciones. Las dos coinciden exactamente con lo que tardó el programa corriendo de verdad.

Atención al programar
  • c_viejo tiene que inicializarse (c_viejo = a) antes del loop. Si no, el primer error = |c − c_viejo| usa memoria basura.
  • La condición del do-while es &&, no ||: "seguir mientras no convergió y no me pasé del máximo". Con || el tope de iteraciones queda anulado — riesgo de loop infinito si el método no converge.
  • Si el intervalo es simétrico y la raíz cae justo en el punto medio (ej. a¹⁰−1 en [0,2], raíz=1), bisección puede converger en 1 sola iteración. Es correcto, pero no es representativo del caso general — no sirve para comparar velocidades de convergencia.
Elegir bien el intervalo: cuidado con raíces espurias

Cuando la ecuación sale de despejar/manipular otra ecuación original (pasar una fracción a la forma f(x)=0, por ejemplo), a veces aparecen raíces "triviales" que matemáticamente cierran pero no tienen sentido físico. Antes de elegir [a,b], conviene graficar la función completa y armar el intervalo para que aísle solo la raíz que buscás.

Caso real (Problema 5, ciclo termodinámico): despejando η(x)=0.3 con x=T₂/T₁ se llega a (1.45/0.7)·(1−1/x) − ln(x) = 0. Esa función tiene una raíz espuria en x≈1 (ahí T₂=T₁, no hay ciclo real — numerador y denominador de η se anulan juntos) y la raíz física de interés bastante más lejos, en x≈5.41. Usar [4,6] como intervalo evita agarrar la de x=1 por accidente.

Falsa posición método cerrado

También parte de [a,b] con cambio de signo, pero en vez de partir al medio, traza la recta secante entre (a,f(a)) y (b,f(b)) y usa el cruce con el eje x como aproximación:

c = a·f(b) − b·f(a)f(b) − f(a)

Actualiza a o b igual que bisección, según el signo de f(a)·f(c).

Ejemplo paso a paso: primera iteración a mano

f(x) = ln(x²+1) − sen(x), intervalo [a,b]=[1, 2] (cambio de signo: f(1)<0, f(2)>0). 

f(1) = ln(2) - sen(1) = -0.1483238042
f(2) = ln(5) - sen(2) =  0.7001404856

c = (a·f(b) − b·f(a)) / (f(b) − f(a))
  = (1·0.7001404856 − 2·(−0.1483238042)) / (0.7001404856 − (−0.1483238042))
  = 0.9967880940 / 0.8484642898
  = 1.1748144336

f(c) = f(1.1748144336) = -0.0554384022
f(a)·f(c) > 0  (los dos negativos)   →   a = c

Nuevo intervalo: [1.1748144336, 2]
No siempre es más rápida que bisección

Cuando la función es muy asimétrica en curvatura cerca de la raíz, un extremo del intervalo se puede quedar "pegado" y casi no avanza — convergencia lineal muy lenta. Caso real: g(a)=a¹⁰−1 en [0,2] necesitó 1147 iteraciones (bisección hizo 1, por el caso particular de arriba). Moraleja: no asumir que un método "más inteligente" siempre gana — depende de la forma de la función.

Mismos cuidados de implementación que bisección

c_viejo = a antes del loop, condición && en el while, y ojo con el max_iter: si es muy chico, puede cortar el método antes de que termine de converger (no es que esté "trabado", solo hace falta más margen).

Punto fijo método abierto

Se reescribe f(x)=0 como x = g(x) y se itera xk+1 = g(xk) a partir de una única semilla x₀.

Condición de convergencia
|g'(x)| < 1  cerca de la raíz
Nota

Chequear g' una sola vez en x₀ (con diferencia finita, (g(x₀+h)−g(x₀))/h) es una simplificación razonable, pero solo es una pista inicial — no garantiza que |g'|<1 se mantenga en todo el recorrido de la iteración.

Ejemplo paso a paso: primera iteración a mano

g(x) = √((x+5)/2), semilla x₀ = 0.

g'(x) = 1 / (4·g(x))     (regla de la cadena sobre g(x)=((x+5)/2)^(1/2))

g(0)  = √(5/2) = 1.5811388301
g'(0) = 1 / (4·1.5811388301) = 0.1581138830

|g'(0)| = 0.1581138830  <  1     →   se cumple el criterio, converge

x1 = g(x0) = g(0) = 1.5811388301
error = |x1 − x0| = 1.5811388301

Cuándo NO converge (ejemplo real)

Ojo con la diferencia entre puntos fijos de g (resolver x=g(x)) y raíces de g (resolver g(x)=0) — son ecuaciones distintas, es fácil despejar de una pensando en la otra.

Con g(x)=x²+x−4, la ecuación x=g(x) da x²−4=0, o sea puntos fijos P=2 y P=−2. Con g'(x)=2x+1:

g'(2) = 5    g'(−2) = −3

|g'(P)| da mayor que 1 en los dos puntos fijos → la iteración directa xk+1=g(xk) diverge, sin importar qué tan cerca arranque la semilla:

Simulación arrancando en x₀=2.01 (a 0.01 del punto fijo)
x0 = 2.010000
x1 = 2.050100
x2 = 2.253010
x3 = 3.329064
x4 = 10.411732
x5 = 114.815895   ← se va al horno
Trampa común

Despejar x de otra forma (ej. x=4−x²) puede parecer una alternativa, pero eso despeja g(x)=0 (sus raíces, ≈1.56 y ≈−2.56), no los puntos fijos de x=g(x). Es una ecuación distinta — y en este caso tampoco converge (φ'(x)=−2x, también mayor que 1 en esas raíces).

La ventaja de g'(P) ≈ 0: de convergencia lineal a cuadrática

Reacomodando la misma ecuación x²=4 de otra forma — ψ(x) = (x + 4/x)/2 (el promedio; matemáticamente es Newton-Raphson aplicado a x²−4=0) — la derivada da:

ψ'(x) = 1/2 − 2/x²    ψ'(2) = 0    ψ'(−2) = 0
Convergencia arrancando en x₀=3 (lejos del punto fijo)
x0 = 3.0000000000
x1 = 2.1666666667
x2 = 2.0064102564
x3 = 2.0000102400
x4 = 2.0000000000   ← precisión de máquina en 4 pasos
Conclusión

Cuando 0 < |g'(P)| < 1, converge pero linealmente (el error se reduce por un factor ≈|g'(P)| en cada paso). Cuando g'(P) ≈ 0, pasa a converger cuadráticamente — el error se eleva al cuadrado en cada paso en vez de multiplicarse por una constante. Es la misma razón por la que Newton-Raphson converge tan rápido: NR es una iteración de punto fijo con φ(x)=x−f(x)/f'(x), y en una raíz simple siempre da φ'(P)=0.

Newton-Raphson método abierto

xk+1 = xk − f(xk)f'(xk)

Converge cuadráticamente (mucho más rápido que los métodos cerrados) cuando converge, pero necesita la derivada analítica y una buena semilla.

Atención

Revisar que |f'(xk)| no sea ~0 antes de dividir — si no, el paso explota o se vuelve inestable.

Ejemplo paso a paso: primera iteración a mano

f(x) = xx − 5, f'(x) = xx·(ln(x)+1), semilla x₀=1.

f(1)  = 1^1 - 5 = -4
f'(1) = 1^1·(ln(1)+1) = 1·(0+1) = 1

x1 = x0 − f(x0)/f'(x0) = 1 − (−4)/1 = 5

error = |x1 − x0| = |5 − 1| = 4

Secante método abierto

Igual que Newton, pero aproxima la derivada con diferencia finita entre los dos últimos puntos — no hace falta la derivada analítica, pero se necesitan 2 semillas.

xk+1 = xk − f(xk)·(xk − xk−1)f(xk) − f(xk−1)
Atención

Revisar que f(xk) − f(xk−1) no sea ~0 antes de dividir.

Ejemplo paso a paso: primera iteración a mano

f(x) = x² − 9x + 2, semillas x₀=0, x₁=1.

f(x0) = f(0) = 0 - 0 + 2 =  2
f(x1) = f(1) = 1 - 9 + 2 = -6

x2 = x1 − f(x1)·(x1−x0) / (f(x1)−f(x0))
   = 1 − (−6)·(1−0) / (−6−2)
   = 1 − (−6)/(−8)
   = 1 − 0.75
   = 0.25

error = |x2 − x1| = |0.25 − 1| = 0.75

Raíz n-ésima Newton-Raphson especializado

Newton-Raphson aplicado directo a f(x) = xn − A (buscar la raíz n-ésima de A) se simplifica a una fórmula cerrada — no hace falta calcular f ni f' por separado en cada paso.

n=2 (raíz cuadrada)
pk = ½·(pk−1 + A/pk−1)
n=3 (raíz cúbica)
pk = (2·pk−1 + A/pk−1²) / 3

Ejemplo paso a paso: primera iteración a mano

A=10, n=2 (raíz cuadrada de 10), semilla p₀=3.

p1 = 0.5·(p0 + A/p0)
   = 0.5·(3 + 10/3)
   = 0.5·6.3333333333
   = 3.1666666667

error = |p1 − p0| = 0.1666666667

(valor exacto: √10 = 3.1622776602 — a una sola iteración ya está a 0.0044 de distancia)

Plantear f(x)=0 a partir de un problema

A veces no te dan la ecuación servida — hay que armarla a partir de la geometría o la física del enunciado. Tres ejemplos reales donde hubo que derivarla desde cero.

Contenedor sin tapa (recortar esquinas)

De una hoja de 10×16, se recorta un cuadrado de lado x en cada esquina y se doblan los bordes: queda una caja sin tapa con altura=x, largo=16−2x, ancho=10−2x. Volumen: V(x) = x(16−2x)(10−2x). Igualando a un volumen pedido y desarrollando:

x(16−2x)(10−2x) = 100  →  f(x) = x³ − 13x² + 40x − 25 = 0
Filtro físico

3 raíces matemáticas: 0.839, 3.402, 8.759. Como hace falta 10−2x>0, el dominio válido es 0<x<5 — la raíz 8.759 queda afuera (da ancho negativo). Dos soluciones físicamente válidas: x≈0.839 y x≈3.402.

Catenaria (cable colgante)

El enunciado ya da la ecuación b = C·cosh(a/C) − C (incógnita C), solo hay que pasarla a la forma f(C)=0:

f(C) = C·cosh(a/C) − C − b = 0
Verificado

Con a=12, b=5: C ≈ 15.167028341664.

Esfera flotando (principio de Arquímedes)

Acá no viene ninguna ecuación en el enunciado — sale de igualar el peso de la esfera con el peso del agua desplazada (densidad del agua = 1 gr/cm³):

Volumen del casquete esférico sumergido, altura d, esfera de radio r
Vcasquete(d) = π·d²3·(3r − d)
ρ·43πr³ = π·d²3(3r−d)   →  f(d) = d³ − 3r·d² + 4ρr³ = 0
Verificado

Con r=10, ρ=0.638: f(d)=d³−30d²+2552=0. Raíces: 26.31, 11.86, −8.18. Filtro físico: 0<d<2r=20 (la profundidad sumergida no puede superar el diámetro) → única válida: d ≈ 11.8615 cm.

El patrón se repite

Mismo tema que en el Problema 5 de bisección (el ciclo termodinámico, más arriba): plantear la ecuación no alcanza — casi siempre hay que filtrar las soluciones matemáticas según el dominio físico real de la variable (un ancho no puede ser negativo, una profundidad no puede superar el diámetro, etc.). Conviene siempre preguntarse qué rango tiene sentido antes de mirar las raíces.

Capítulo 2 — Sistemas de ecuaciones lineales completo

Eliminación gaussiana

Triangulación

Pseudocódigo (1-indexado, como lo da la profesora)
Do i = 1,...,n-1        ← Pivoteo
  Do j = i+1,...,n
    factor = -a_ji / a_ii
    Do k = i+1,...,n
      a_jk = a_ik·factor + a_jk
    end Do
    b_j = b_i·factor + b_j
  end Do
end Do

Determinante

Producto de la diagonal ya triangulada: det = a₁₁·a₂₂·…·aₙₙ. Si det = 0 → matriz singular, no tiene solución única.

Retrosustitución

xi = bi − Σj>i aij·xjaii   (empezando por xn y bajando hasta x₁)
El error que más se repite en todo el curso

El pseudocódigo de la profesora es 1-indexado (arranca en 1, a₁₁ es el primer elemento). Los arrays de C++ son 0-indexados. Hay que correr los puntos de arranque de los loops un lugar (i=1→i=0, i=2→i=1, a[1][1]→a[0][0]) — pero ojo: los límites superiores (i<n-1, j<n, etc.) casi siempre ya quedan bien escritos tal cual, sin tocar nada.

Interpolación polinómica = sistema de Vandermonde

"Encontrar el polinomio y=A+Bx+Cx²+Dx³ que pasa por 4 puntos dados" no es un tema aparte — es una aplicación directa de resolver un sistema lineal. Por cada punto (x_i, y_i) conocido, se arma una ecuación evaluando el polinomio genérico ahí: A + B·x_i + C·x_i² + D·x_i³ = y_i. Con 4 puntos, quedan 4 ecuaciones para las 4 incógnitas A,B,C,D — se resuelve con Gauss/Gauss-Jordan como cualquier otro sistema. La matriz que se arma (filas [1, x_i, x_i², x_i³]) se llama matriz de Vandermonde.

Trampa: el coeficiente de A siempre es 1

El coeficiente de A en cada fila es siempre 1, sin importar el valor de x_i — ni siquiera se anula en x_i=0 (lo que se anula ahí son los términos Bx, Cx², Dx³, no el de A, que no depende de x). Un error común es poner 0 en esa columna para las filas donde no es el punto "especial" — eso arma mal el sistema.

Lo traicionero: si el punto (0,y₀) tiene y₀=0, la solución para A da 0, y ahí 0·A y 1·A dan lo mismo (cero) — el error queda "tapado" y el resultado sale bien por casualidad. Si A hubiese dado cualquier otro valor, el error sí cambia la respuesta (lo comprobamos forzando A=5: con el `0` mal puesto daba B,C,D = -0.167, 1.5, -0.333; con la matriz bien armada daba -9.33, 6.5, -1.17 — completamente distinto).

Pivoteo parcial

Si |a_ii| da muy chico, buscar en esa columna la fila con mayor valor absoluto y swapear filas (y también b) antes de seguir.

Dos bugs reales encontrados acá
  • Guardar el valor absoluto (fabs(...)) al comparar y al actualizar el "mayor valor" — si se guarda el valor con signo, un negativo grande puede perder la comparación contra un positivo chico.
  • Al swapear dos filas, mover todas las columnas (de 0 a n-1) — arrancar el loop del swap en 1 en vez de 0 deja la columna 0 sin intercambiar (mismo error de indexado de arriba, escondido en otro lado del código).

Gauss vs. Gauss-Jordan

Dan siempre el mismo resultado (verificado) — la diferencia es cuánto se triangula:

  • Gauss: ceros solo por debajo de la diagonal, después retrosustitución (despejar desde x_n hacia atrás).
  • Gauss-Jordan: además elimina por encima de la diagonal (columna pivote de atrás para adelante) y normaliza cada fila — queda [I|x], se lee la solución directo, sin retrosustitución. Hace más cuentas que Gauss (~50% más), pero si el enunciado pide Gauss-Jordan específicamente, hay que mostrar esa eliminación extra, no alcanza con el resultado triangulado + retrosustitución.
Cuidado con el determinante en Gauss-Jordan

El determinante hay que calcularlo apenas termina la triangulación hacia abajo (producto de la diagonal), antes de normalizar filas. Si se normaliza primero (dividir cada fila por su pivote para dejar la diagonal en 1) y se calcula el determinante después, va a dar siempre 1 — mal.

Otro cuidado con el determinante: el signo cambia con cada swap

Cada vez que el pivoteo intercambia dos filas de verdad, el signo del determinante real se invierte — si no se compensa, el producto de la diagonal final da el valor absoluto correcto pero el signo equivocado cuando hubo una cantidad impar de swaps. Se arregla con una variable signoDet (arranca en 1, se multiplica por -1 en cada intercambio real) que multiplica al producto de la diagonal.

Este bug estuvo escondido varios ejercicios: como los sistemas anteriores no necesitaban pivotear de verdad, el código daba bien "por accidente". Recién se destapó en un ejercicio que obligaba a pivotear (enunciado: a11=4, a22 queda en 0 después de triangular, hace falta swap) — el determinante daba -4 en vez de +4. Buena lección general: un bug en una rama de código que nunca se ejecuta no se nota hasta que un caso de prueba fuerza justo esa rama.

Matrices mal condicionadas

A veces el sistema en sí es "frágil": un cambio mínimo en un dato de entrada produce un cambio enorme en la solución. Se detecta comparando el determinante contra la norma de Frobenius de la matriz:

‖A‖ = √( Σi=1n Σj=1n Aij² )

Si det(A) da chico comparado con ‖A‖, la matriz es "cuasi-singular" — mal condicionada. No hay un umbral fijo, es una comparación de órdenes de magnitud.

Caso real — sistema de interpolación con matriz mal condicionada

Cambiando una sola celda de la matriz (A₁,₁) apenas un 0.005% (20514→20515), sin tocar nada más:

                c1,c2,c3,c4                          det(A)   ||A||
original:       1, 0, 0, 0                            144    21518.5
A11=20515:      0.642857, 3.75, -12.3929, 12.75        224    21519.5

‖A‖ casi no se movió, pero det(A) cambió un 55% y la solución cambió por completo. Esa sensibilidad extrema a una perturbación mínima es justamente la señal de que la matriz está mal condicionada — el determinante es insignificante comparado con la norma.

Ojo al calcular ‖A‖ en el código

Hay que calcularla con la matriz original, antes de triangular — triangular() pisa las entradas de abajo de la diagonal con ceros, así que si se calcula después, la norma sale mal (le faltan términos).

Método de Jacobi iterativo

Para resolver Ax=b: se despeja cada x_i de su propia ecuación, usando siempre los valores de la iteración anterior (a diferencia de Gauss-Seidel, que ya usa los valores nuevos apenas se calculan).

xi(k+1) = bi − Σj≠i aij·xj(k)aii

Tres cosas para implementarlo

  1. Asegurar a_ii ≠ 0 — se garantiza pidiendo que la matriz sea diagonalmente dominante: |a_ii| > Σj≠i |a_ij| en cada fila. Condición suficiente, no necesaria (puede converger igual sin serlo).
  2. Inicializar el vector X⁽⁰⁾ = (0,0,…,0).
  3. Criterio de corte por tolerancia, en base al error.

Error

e = ‖Xnuevo − Xviejo‖  (norma euclídea → error absoluto)
E = e‖Xnuevo‖ × 100  (error porcentual)

Ejemplo paso a paso: primera iteración a mano

Sistema 3x₁+x₂=10, −x₁+5x₂=18, x₀=(0,0) (solución exacta: (2,4)). 

x1 = (10 − x2_viejo) / 3 = (10−0)/3 = 3.3333333333
x2 = (18 + x1_viejo) / 5 = (18+0)/5 = 3.6000000000   ← usa x1_VIEJO (0), no el recien calculado

error estimado = ‖Xnuevo−Xviejo‖ = √(3.3333333333² + 3.6²)               = 4.9062318648
error exacto   = ‖Xnuevo−Xexacto‖ = √((3.3333333333−2)² + (3.6−4)²)      = 1.3920408679
Bug encontrado: la suma no se resetea por fila

suma tiene que volver a 0 en cada fila i (adentro del loop de i, antes del loop de j) — no una sola vez por iteración global. Si no, se arrastra entre filas y la fórmula de Jacobi queda mal.

Buena práctica

Guardar el error de la iteración anterior y, si el error nuevo es mayor que el anterior, cortar con un aviso de "el método no converge" — Jacobi no siempre converge, y así se detecta a tiempo en vez de iterar al pedo.

Gauss-Seidel iterativo

Igual que Jacobi, pero usando el valor de x_j ya actualizado en la misma pasada apenas se calcula, en vez de esperar a la iteración siguiente. Por eso converge bastante más rápido que Jacobi cuando converge.

xinuevo = bi − Σj<i aij·xjnuevo − Σj>i aij·xjviejoaii
Truco de implementación

No hace falta mantener dos arrays separados (Xviejo/Xnuevo) como en Jacobi — alcanza con un solo array X actualizado en el lugar. Cuando se calcula X[i], las posiciones X[0..i-1] ya tienen los valores nuevos de esta pasada, y X[i+1..n-1] todavía tienen los viejos (no se tocaron todavía) — exactamente lo que pide la fórmula, sin necesitar ningún caso especial para i=1. Eso sí, conviene guardar una copia de X de antes de la pasada (Xviejo) solo para poder calcular el error al final.

Ejemplo paso a paso: primera iteración a mano

Mismo sistema que en Jacobi (para comparar directo): 3x₁+x₂=10, −x₁+5x₂=18, x₀=(0,0).

x1 = (10 − x2_viejo) / 3 = (10−0)/3            = 3.3333333333
x2 = (18 + x1_NUEVO) / 5 = (18+3.3333333333)/5 = 4.2666666667   ← ya usa el x1 recien actualizado

error estimado = ‖Xnuevo−Xviejo‖  = √(3.3333333333² + 4.2666666667²)          = 5.4143841345
error exacto   = ‖Xnuevo−Xexacto‖ = √((3.3333333333−2)² + (4.2666666667−4)²) = 1.3597385370
Verificado: converge mucho más rápido que Jacobi

Mismo sistema DD ([[3,1,1],[0,2,1],[1,3,5]], b=[5,3,9]), misma tolerancia:

Jacobi:        25 iteraciones
Gauss-Seidel:   9 iteraciones

Las dos convergen a la misma solución (1,1,1).

Gauss-Seidel con relajación

Después de calcular x_i con la fórmula normal de Gauss-Seidel, se mezcla con el valor viejo:

Xn[i] = w·Xn[i] + (1−w)·Xv[i]    w ∈ [0,2]
  • w=1 → Gauss-Seidel tradicional (sin cambios).
  • w∈(0,1) → sub-relajación: sirve para hacer converger un sistema que de otra forma no converge.
  • w∈(1,2] → sobre-relajación: le da más peso a los valores nuevos, para acelerar un método que ya converge (no siempre ayuda — depende de la matriz).
No hay que calcular w

La elección del w óptimo es específica de cada problema y se determina empíricamente — para los ejercicios de la materia, si hace falta relajación, w viene dado en el enunciado, no hay que calcularlo.

El orden de las filas importa

A diferencia de eliminación gaussiana (donde el pivoteo reordena filas libremente sin cambiar si el sistema tiene solución), Jacobi y Gauss-Seidel no son invariantes al orden de las ecuaciones. El mismo sistema, reescrito con las filas en otro orden, puede pasar de converger rapidísimo a divergir sin remedio.

Caso real: mismo sistema, dos órdenes de filas

Orden 1 (diagonalmente dominante): 4x-y+z=7, 4x-8y+z=-21, -2x+y+5z=15 → Jacobi converge en 13 iteraciones, Gauss-Seidel en 8. Los dos dan x=2, y=4, z=3.

Orden 2 (mismas 3 ecuaciones, filas 1 y 3 intercambiadas): deja de ser DD en 2 de las 3 filas → ninguno de los dos métodos converge.

Para comprobar que diverge de verdad (no es solo el corte conservador del programa), dejando correr la iteración sin cortar, ‖x‖ crece sin límite y con signo oscilante:

Jacobi:        10.6 → 41 → 100 → 362 → 960 → 3496 → ... → 3.1×10^6   (iter 12)
Gauss-Seidel:  36.7 → 288 → 2415 → 20140 → ... → 4.7×10^11          (iter 12)
Nota aparte (no vista en clase, opcional)

La condición matemática exacta de convergencia (necesaria y suficiente, a diferencia de la DD que solo es suficiente) es que el radio espectral de la matriz de iteración sea menor a 1. Para el "Orden 2" de arriba da 3.10 (Jacobi) y 8.35 (Gauss-Seidel) — muy por encima de 1, lo que confirma que ninguna semilla inicial converge (no es mala suerte con el punto de partida). No hace falta esto para resolver el ejercicio de la materia — alcanza con mostrar que no es DD y que la sucesión diverge en la práctica. Se deja acá solo como referencia.

Cómo encontrar un orden que sí converja

Si te dan una matriz que no converge tal como está ordenada, hay un truco rápido para encontrar un reordenamiento de filas que sí sea diagonalmente dominante, sin tener que probar todas las permutaciones a mano:

Para cada fila, fijate en qué columna está el coeficiente de mayor valor absoluto — ese es el mejor candidato para quedar en la diagonal de esa fila. Si asignás cada fila a la columna de su coeficiente más grande, y esa asignación no repite ninguna columna (cada fila "elige" una distinta), esa reordenación es DD.

Ejemplo: sistema (2) de arriba
Fila A: -2x + y + 5z = 15   → [-2, 1, 5]  → el mayor es 5 (col. z)
Fila B:  4x - 8y + z = -21  → [4, -8, 1] → el mayor es -8 (col. y)
Fila C:  4x - y  + z = 7    → [4, -1, 1] → el mayor es 4 (col. x)

Sin conflicto (cada una eligio una columna distinta) → orden nuevo:
  fila que quiere columna x primero (Fila C)
  fila que quiere columna y segunda (Fila B)
  fila que quiere columna z tercera (Fila A)

Eso da exactamente el "Orden 1" de arriba — el que ya sabíamos que convergía.

  • Si dos filas compiten por la misma columna, no hay asignación directa — hay que probar a mano cuál cede esa columna y se queda con su segunda opción, y volver a chequear DD.
  • El truco encuentra un orden DD, que es condición suficiente — puede existir un orden que converja sin ser DD, pero para los ejercicios de la materia, si existe un reordenamiento que sirva, este método normalmente lo encuentra directo.
  • Si ninguna asignación logra que cada fila domine en su columna, es señal de que ese sistema no tiene ningún reordenamiento que lo vuelva DD (aunque podría converger igual, sin garantía).

Cuándo conviene abandonar el iterativo e ir directo a Gauss

A veces el problema no es que falte encontrar el reordenamiento correcto — es que ningún reordenamiento va a funcionar, porque cada fila individualmente ya está al límite (empatada, no estrictamente dominante) sin importar qué columna se le asigne.

Caso real: matriz tridiagonal 100×100

Sistema banda con diagonal 2 y un 1 a cada lado (x_{i-1} + 2x_i + x_{i+1} = 6). Para casi todas las filas: diagonal =2, suma de los otros dos =1+1=2. 2 > 2 es falso — empate, no dominancia estricta. Y esto no depende del orden de las filas: por más que reordenes, cada fila individual sigue empatada consigo misma, porque el empate viene de sus propios coeficientes, no de en qué posición está.

Acá no vale la pena seguir insistiendo con Jacobi/Gauss-Seidel buscando un orden mágico que no existe. La salida es usar Gauss (método directo): no depende de ningún criterio de dominancia, y para tamaños como n=100 sigue siendo trivial en tiempo de cómputo (~100³ operaciones, milisegundos).

Caso puntual: un "no converge" ¿es real, o es demasiado lento?

El chequeo de divergencia del pseudocódigo (comparar el error contra el de la iteración anterior) a veces corta un caso que en el fondo sí converge — solo que muy lento, y sin bajar de forma perfectamente monótona.

Ejemplo real

Matriz [[5,7,6,5],[7,10,8,7],[6,8,10,9],[5,7,9,10]], b=[23,32,33,31] — ninguna fila es DD.

  • Jacobi: diverge de verdad — el error crece feo desde el arranque (radio espectral de la matriz de iteración ≈ 2.48).
  • Gauss-Seidel: con el algoritmo tal como se da en clase, corta en la iteración 31 con "no converge" — el error venía bajando de 4.6 a 0.0045 durante 30 iteraciones, y ahí tuvo un repunte mínimo (0.004536 → 0.004570) que dispara el corte.

Cómo distinguir uno del otro, mirando la salida:

  • Si el error venía creciendo feo desde el principio (como Jacobi acá) → divergencia real, sin vuelta.
  • Si el error venía bajando de forma consistente durante muchas iteraciones y recién al final tuvo un repunte chico (como Gauss-Seidel acá) → sospechoso de ser solo lento, no necesariamente divergente de verdad.
  • Ante la duda, se puede correr una versión con el chequeo de divergencia relajado (que solo corte si el error realmente explota) y muchas más iteraciones de margen, para ver qué pasa en el largo plazo — sin usar esa versión como la respuesta a entregar, solo para entender qué está pasando.
En este caso puntual

Dejándolo correr sin el corte temprano, Gauss-Seidel termina convergiendo — pero recién en la iteración 1276 (con w=1, tolerancia 1e-4).

Trampa extra: el criterio de corte puede mentir

En esa iteración 1276, el error "sucesivo" (‖Xk+1-Xk‖) daba 9.99×10⁻⁵ — ya por debajo de la tolerancia. Pero el error real contra la solución exacta era 0.032, más de 300 veces mayor. Esto pasa porque cuando la convergencia está casi estancada (radio espectral pegado a 1), dos iteraciones consecutivas se parecen mucho entre sí aunque las dos estén todavía lejos de la respuesta real — el criterio de corte mide cuánto cambió de un paso al otro, no cuánto falta para la solución exacta.

Criterio de corte por residuo

Alternativa a comparar dos iteraciones consecutivas: reescribiendo Ax=b como Ax−b=0, se puede medir directamente qué tan bien x_k resuelve la ecuación real, en vez de cuánto se movió respecto al paso anterior:

residuok = ‖A·xk − b‖

Ventaja sobre ‖Xk+1-Xk‖: no lo puede engañar una racha de pasos chiquitos que no reflejan la distancia real a la respuesta — justo la trampa de arriba. Se implementa igual que antes, solo cambiando qué se calcula como "error" en cada iteración (y qué se compara contra la tolerancia).

Verificado: Problema 2 resuelto de nuevo con este criterio

Sistema a) (bien condicionado): prácticamente lo mismo que antes — Jacobi 48 iteraciones (antes 47), Gauss-Seidel 14 (igual). Mismo resultado x=(1,1,1).

Sistema b) (el caso límite de arriba): sigue dando "no converge" para los dos métodos con el algoritmo dado — el criterio de residuo no lo arregla mágicamente, sigue siendo el mismo sistema límite.

Donde se ve la ventaja de verdad: dejando correr el sistema b) más allá del corte, comparando los dos criterios a la misma tolerancia numérica (1e-4):

Criterio                    termina en iter   error real vs. solucion exacta
Diferencia sucesiva              1276              0.032
Residuo ||Ax-b||                 1750              0.0074   (~4x mas preciso)

A la misma tolerancia, el criterio de residuo tarda más en darse por satisfecho, pero cuando lo hace el resultado es varias veces más preciso — porque exige que la ecuación esté realmente resuelta, no solo que el último paso haya sido chico.

Sistemas de banda: aprovechar la estructura

Cuando una matriz tiene muchos ceros lejos de la diagonal (estructura de banda), no hace falta recorrer las n columnas en cada fila durante la iteración — alcanza con mirar la banda.

Ancho de banda
p = max{ |i−j| } para todo (i,j) con A[i][j] ≠ 0

Se calcula recorriendo toda la matriz una sola vez — es un algoritmo general, sirve para cualquier matriz, no hay que asumir nada de su estructura de antemano. Encontrado p, en Gauss-Seidel cada fila i recorre solo j ∈ [i−p, i+p] en vez de j ∈ [0, n-1] — fuera de ese rango ya se sabe que es cero, ni vale la pena mirarlo.

Verificado: sistema pentadiagonal 50×50

Diagonal 12, offset ±1 -2, offset ±2 1 (ancho de banda real = 2, detectado automáticamente). Mismo resultado con las dos versiones (12 iteraciones, misma solución) — la diferencia es solo velocidad:

Denso: 12.10 us por resolucion  (recorre las 50 columnas por fila)
Banda:  4.37 us por resolucion  (recorre ~5 columnas por fila)
Speedup: 2.77x

Con n=50 la diferencia ya se nota. Crece mucho más para n grande: el denso escala con n² por iteración, el de banda con n·p — la ventaja del ancho de banda se vuelve enorme cuanto más grande el sistema (y más angosta la banda relativa a n).

Generar sistemas grandes: programáticamente, no a mano

Un sistema de 50×50 (o más) no se puede tipear a mano en un archivo de texto. Conviene escribir un programita en C++ que arme el patrón (diagonal, offsets, condiciones de borde en las primeras/últimas filas) con un loop, y lo escriba a un archivo con el mismo formato [A|b] que ya se lee siempre — así el sistema de prueba queda reproducible y es parte de la propia entrega, no algo hecho aparte a mano.

Relajación en la práctica: comparación real de ω

Caso real: sistema 6×6 tridiagonal ampliado (bandas hasta ±2), no diagonalmente dominante (4 de las 6 filas fallan la DD) — y aun así Gauss-Seidel converge sin problemas. Es la prueba concreta de que DD es condición suficiente, no necesaria.

Verificado
w = 1,0 (Gauss-Seidel sin relajacion):  43 iteraciones
w = 1,1 (sobrerelajacion):              39 iteraciones  (~9% menos)

Misma solución en los dos casos: x=(2, 0, 4, 4, 0, 2). Con un sistema que ya converge razonablemente bien, un ω levemente mayor a 1 acelera un poco sin desestabilizar.

Detalle de borde, sin importancia práctica

En este sistema, dos filas tienen la diagonal igual (no mayor) a la suma de las demás — no cumplen la DD estricta tampoco, pero como el chequeo de código usa < estricto, no se marcan como "no DD". No cambia el resultado del ejercicio, es solo una curiosidad del caso límite exacto.

Capítulo 3 — Interpolación

Idea general

Dado un conjunto de n+1 datos (x₀,y₀), (x₁,y₁), …, (xₙ,yₙ) con los xᵢ todos distintos, existe uno y solo un polinomio de grado ≤n que pasa exactamente por todos ellos. Sirve para estimar un valor intermedio (un y para un x que no está en la tabla de datos) sin conocer la función real detrás de los datos.

Forma general del polinomio de grado n
Pn(x) = a₀ + a₁x + a₂x² + … + aₙxⁿ

Dos formas de conseguirlo: Lagrange (evalúa directo, sin armar el polinomio) y coeficientes indeterminados (arma el polinomio completo, resolviendo un sistema lineal — ya sabemos hacer esto).

Lagrange

Pn(x) = Σk=0n yk·Cnk(x)     con     Cnk(x) = Πi≠k x − xixk − xi

Cada Cnk(x) ("cardinal" de Lagrange) tiene una propiedad clave que hace que todo funcione:

Cnk(xk) = 1    Cnk(xj) = 0  (para j≠k)

Por eso, al evaluar en cualquiera de los puntos originales xj, todos los términos de la suma se anulan menos uno, y queda Pn(xj) = yj·1 = yj — el polinomio pasa exacto por los datos, por construcción.

Pseudocódigo (evalúa Pn en un punto x̂, no arma el polinomio)
Leer datos y guardarlos: x[n+1], y[n+1]
Ingresar x_hat
suma = 0
Do k = 0,...,n
    prod = 1
    Do i = 0,...,n
        if (i != k)
            prod = prod * (x_hat - x[i]) / (x[k] - x[i])
        end if
    end Do
    suma = suma + y[k]*prod
end Do
Mostrar resultado: suma
Desventaja

Lagrange solo devuelve el valor interpolado en un punto puntual — no arma la forma funcional del polinomio (los coeficientes a₀,a₁,...). Si hace falta el polinomio completo (por ejemplo, para derivarlo o graficarlo), conviene el método de coeficientes indeterminados.

Coeficientes indeterminados (Vandermonde)

Cada punto (xi,yi) da una ecuación lineal en las incógnitas a₀,...,aₙ: a₀ + a₁xi + a₂xi² + … + aₙxiⁿ = yi. Con n+1 puntos quedan n+1 ecuaciones para n+1 incógnitas — un sistema lineal Ax=b (la misma matriz de Vandermonde que ya vimos en interpolación polinómica de Eliminación gaussiana), que se resuelve con Gauss + pivoteo, tal como ya lo tenemos hecho.

Pseudocódigo
Leer los datos y guardarlos: x[n+1], y[n+1]

Armar A y b:
Do i = 0,...,n
    Do j = 0,...,n
        A[i][j] = pow(x[i], j)
    end Do
    b[i] = y[i]
end Do

Resolver el sistema: call GaussPivot(A, b) -> devuelve los a_i

Si evaluamos en x_hat:
    suma = 0
    Do i = 0,...,n
        suma = suma + a[i]*pow(x_hat, i)
    end Do
    Mostrar resultado: suma

Cómo verificar que el resultado está bien

  1. El chequeo básico, siempre válido: evaluar el polinomio en los puntos originales y confirmar que Pn(xi) = yi exacto, para todos los i. Si no da exacto ahí, hay un error en el cálculo — no hace falta ni conocer la respuesta de antemano.
  2. Comparar los dos métodos entre sí. Lagrange y coeficientes indeterminados construyen matemáticamente el mismo polinomio (por unicidad), así que evaluados en el mismo punto tienen que dar exactamente igual. Si difieren, hay un bug en alguno de los dos.
  3. ¿El valor es razonable? — con cuidado. Para polinomios de grado bajo y datos que no cambian mucho, el valor interpolado suele caer entre los y vecinos. Pero no es una regla general: un polinomio de grado alto puede oscilar entre los puntos (fenómeno de Runge) y dar valores fuera de ese rango sin que sea un error. Sirve como señal de alerta, no como prueba.
  4. Interpolar vs. extrapolar. Evaluar dentro del rango [x₀, xₙ] (interpolar) es razonablemente confiable. Evaluar afuera de ese rango (extrapolar) es mucho menos confiable — nada garantiza que el polinomio se siga pareciendo a los datos reales más allá de donde fue ajustado.
Ejemplo verificado

Puntos (0,1), (3,2), (6,8) → polinomio de grado 2.

P₂(x) = 1 − 0,5x + 0,277778x²

Chequeo en los puntos originales: P₂(0)=1 ✓, P₂(3)=2 ✓, P₂(6)=8 ✓.

Interpolando en x=2 (adentro del rango): Lagrange y coeficientes indeterminados dan los dos P(2) = 1,1111 (=10/9). Coincide.

Interpolando en x=4: P(4) = 3,4444 (=31/9) — cae entre y=2 (en x=3) y y=8 (en x=6), como se esperaba para este caso de grado bajo.

Ojo al buscar una raíz sobre el polinomio interpolante

El polinomio de Lagrange solo tiene garantía de coincidir con la función real en los nodos. En cualquier otro punto — incluida, muchas veces, la raíz que estás buscando — no hay ninguna garantía de qué tan cerca está de la función verdadera. Cuantos menos nodos y más rápido cambie la función entre ellos, peor.

Caso real: 20% de error por confiar en el polinomio lejos de los nodos

Mismo problema, dos formas de buscar la misma raíz — una usando el modelo ajustado (f(x)=ex²-2, de una regresión) y otra usando el polinomio de Lagrange que interpola los mismos 4 puntos de la tabla (x: 0.5, 0.8, 1.3, 2.0): 

                        modelo ajustado (exp)      polinomio de Lagrange
Raiz obtenida:          0.8325546041                0.9992333678
Error absoluto exacto:  7.06e-9                      0.1667
Error porcentual:       8.48e-7 %                    20.02 %

El polinomio interpola perfecto en los 4 puntos de la tabla — pero la raíz real (x≈0.83) cae entre dos nodos bastante separados (0.8 y 1.3), justo donde el cúbico no tiene ninguna obligación de parecerse a la exponencial real. Resultado: 20% de error, nada despreciable. No es un bug — es una consecuencia esperable de interpolar con pocos nodos una función que crece rápido.

Capítulo 4 — Ajuste de curvas

Idea general

Interpolación fuerza al polinomio a pasar exacto por cada punto. Eso funciona bien con datos limpios, pero si los datos vienen de mediciones con error apreciable, forzar el paso exacto por cada uno (ruido incluido) puede dar un polinomio que oscila mucho y no sirve para predecir nada — sobre todo si n es grande. A veces, con solo mirar los datos ("por inspección"), ya se intuye un comportamiento simple (lineal, por ejemplo) escondido detrás del ruido.

Regresión no busca pasar exacto por los puntos — busca la función que quede lo más cerca posible de todos ellos a la vez, aceptando algo de error en cada uno a cambio de una forma simple y estable.

Regresión lineal

El caso más simple: buscar F(x) = ax + b tal que el error cuadrático total sea mínimo. Con ei = |yi − F(xi)|, el "criterio de cuadrados mínimos" busca minimizar:

Sr(a,b) = Σi=0n (yi − axi − b)²

Derivando e igualando a 0 (∂Sr/∂a=0, ∂Sr/∂b=0) se llega a un sistema lineal 2×2 para las incógnitas a,b:

Σxi²  ΣxiΣxi  (n+1)    ab  =  ΣxiyiΣyi
Ejemplo verificado

x: 0, 1, 1.5, 3, 5    y: 1.2, 2.7, 3.9, 7.1, 10 (5 datos)

Sum x^2 = 37.25   Sum x = 10.5
Sum xy  = 79.85   Sum y = 24.9

[37.25  10.5] [a]   [79.85]
[10.5   5   ] [b] = [24.9 ]

a = 1.8132   b = 1.1724

F(x) = 1,81x + 1,17. Para corroborar: evaluar F en cada x y ver si da parecido a las y reales (no exacto, pero cerca).

Coeficiente de correlación

¿Cómo saber si el ajuste lineal es bueno, o si los datos en realidad no tienen ninguna relación lineal y son solo mediciones dispersas de un mismo valor? Se compara la dispersión total de los datos contra el error que deja el ajuste:

St = Σ(yi − ȳ)²  (dispersión total, respecto al promedio)      Sr = Σ(yi − F(xi))²  (error que deja el ajuste)
r = √( (St − Sr) / St )
  • Ajuste lineal perfecto → Sr=0 → r=1.
  • r=0 ⟺ St=Sr: el ajuste no explica nada más de lo que ya explicaba la dispersión estadística de los datos — el "ajuste" no sirvió de nada.
  • Cuanto más cerca de 1 esté r, mejor el ajuste (como referencia informal de tus apuntes: r<0,7 ya se considera medio/malo).
Aplicado al ejemplo anterior

ȳ = 24,9/5 = 4,98    St = 50,35    Sr = 0,378 → r = 0,99624 — muy buen ajuste.

Regresión con funciones arbitrarias

La regresión por cuadrados mínimos no está limitada a rectas ni polinomios — sirve para cualquier función con parámetros a ajustar. La receta es siempre la misma: plantear Sr con la función propuesta, derivar respecto a cada parámetro, igualar a 0, y resolver el sistema lineal resultante (con Gauss, como siempre).

Ejemplo real (P4 - Parcial 1, 2023)

Ajustar F(x) = a·sen(x) + b·cos(x) a 7 puntos. Derivando Sr respecto a a y b:

Σsen²xi  ΣcosxisenxiΣcosxisenxi  Σcos²xi    ab  =  ΣyisenxiΣyicosxi

Mismo sistema 2×2 de siempre, distintas sumas — resolver con Gauss. Con los 7 datos del parcial: a=0,678, b=-1,928, r=0,970 (buen ajuste, no perfecto).

Linealizar modelos no lineales

La sección anterior sirve cuando el modelo ya es lineal en sus parámetros (a·sen(x)+b·cos(x) es lineal en a,b, aunque tenga senos y cosenos adentro). Pero hay modelos donde eso no alcanza — por ejemplo F(x) = a·ex² + b. Ahí "regresión lineal" no significa ajustar una recta en x — significa inventar una variable nueva que sí haga que el modelo sea una recta.

El truco: si le ponés un nombre a la parte no lineal, u = ex², el modelo queda F = a·u + b — una recta común, en u en vez de en x.

Receta
1. Identificar la parte no lineal del modelo y llamarla u (ej: u = exp(x^2))
2. Calcular u_i = esa formula, para cada x_i de la tabla (el y_i no cambia)
3. Armar una tabla nueva (u_i, y_i)
4. Correr una regresion lineal COMUN sobre (u,y): y = a*u + b
5. Los a,b que salen son los del modelo original -- no hace falta "deshacer" nada
El error más fácil de cometer

Tirarle la tabla (x,y) cruda a una regresión lineal, sin linealizar antes. Compila y da un resultado — pero es el ajuste de un modelo distinto (una recta en x, no la exponencial que pide el enunciado). La señal de alarma es un r mediocre que no tiene por qué estar mal: en un caso real, ajustar y contra x cruda dio r=0,896 (dudoso para un ajuste que se supone bueno); linealizando con u=exp(x²) y ajustando contra eso, el mismo dataset dio r=0,9999999999 — la diferencia entre un ajuste mediocre y uno prácticamente perfecto era, exclusivamente, no haber linealizado.

Ejemplo real

Tabla: x: 0.5, 0.8, 1.3, 2.0   y: -0.716, -0.103, 3.419, 52.598. Modelo: F(x)=a·ex²+b.

u_i = exp(x_i^2):  1.2840254167, 1.8964808793, 5.4194807051, 54.5981500331

Regresion lineal de y contra u:
  a (pendiente)  = 0.999996  ~ 1
  b (ordenada)   = -1.99997  ~ -2
  r = 0.9999999999

Una vez que tenés a,b, el resto (buscar la raíz, comparar contra el polinomio de Lagrange, etc.) sigue exactamente igual que con cualquier otro modelo ya ajustado.

Regresión polinómica (caso general)

Generaliza la regresión lineal a un polinomio de grado p cualquiera: F(x) = a₀ + a₁x + a₂x² + … + aₚxᵖ. Hacen falta al menos p+1 puntos para que el sistema quede determinado. Derivando Sr respecto a cada ak (p+1 derivadas) se llega a un sistema lineal (p+1)×(p+1), con esta forma general para cualquier p (las "ecuaciones normales"):

Aℓm = Σi=0n xiℓ+m      bℓ = Σi=0n yi·xiℓ      (ℓ,m = 0,...,p)

Con p=1 esto se reduce exactamente a la matriz de regresión lineal de arriba — es el mismo caso, generalizado.

Pseudocódigo
Ingresar los datos (x,y) -> guardar en x[n+1], y[n+1]
Ingresar p (grado del polinomio)
Si (n+1) < (p+1) -> imprimir "no hay suficientes datos", parar

Armar A, b:  (A[p+1][p+1], b[p+1])
Do l = 0,...,p
    sumaAy = 0
    Do i = 0,...,n
        sumaAy = sumaAy + pow(x[i],l)*y[i]
    end Do
    b[l] = sumaAy

    Do m = 0,...,p
        sumaAx = 0
        Do i = 0,...,n
            sumaAx = sumaAx + pow(x[i], l+m)
        end Do
        A[l][m] = sumaAx
    end Do
end Do

Llamar a Eliminacion Gaussiana(A,b) -> devuelve los a_k
Mostrar resultados

Calcular el coeficiente de correlacion:
    yprom = (suma de y[i]) / (n+1)
    sumaT = 0, sumaR = 0
    Do i = 0,...,n
        sumaT = sumaT + (y[i]-yprom)^2
        fi = suma_j( a[j]*pow(x[i],j) )   para j=0,...,p
        sumaR = sumaR + (y[i]-fi)^2
    end Do
    r = sqrt( (sumaT-sumaR)/sumaT )

La gran mayoría de estos programas comparten el mismo esqueleto (leer archivo de puntos/matriz, armar el sistema, Gauss con pivoteo parcial) y solo cambian en una línea marcada explícitamente con un comentario tipo // ACA se elige el problema — la f(x), las funciones base φ, o el criterio de corte. Antes de correr cualquiera de estos para un ejercicio nuevo, ubicar esa línea puntual y confirmar que coincide con el enunciado, en vez de asumir que "ya está bien" porque compiló y corrió sin errores.

Transversal — tipos de error

Estimado vs. exacto, absoluto vs. porcentual

Estos cuatro nombres se mezclan todo el tiempo en los enunciados, y en realidad son dos ejes independientes que se cruzan. El criterio es el mismo para bisección, falsa posición, punto fijo, Newton-Raphson, secante, Jacobi y Gauss-Seidel — solo cambia la fórmula puntual de cada método.

Eje 1 — ¿contra qué se compara?
  • Estimado: compara la iteración actual contra la iteración anterior (x_nuevo vs x_viejo). Es el único que un programa real puede calcular — nunca conoce la solución exacta — y es lo que se usa como criterio de corte del while.
  • Exacto: compara la aproximación actual contra la solución analítica conocida (x_aprox vs x_exacto). Solo se puede calcular en ejercicios donde el enunciado permite obtener la raíz real a mano (el punto "a" del parcial modelo, por ejemplo) — sirve para verificar qué tan buena es la estimación, no como criterio de corte del programa.
Eje 2 — ¿absoluto o porcentual?
  • Absoluto: la diferencia cruda, sin normalizar. error = |A − B|.
  • Porcentual: el mismo valor absoluto, dividido por algo de referencia y ×100 para expresarlo como %.

Las cuatro combinaciones

Estimado — absoluto
error = |xnuevo − xviejo|
Estimado — porcentual (fórmula (#) del parcial modelo, para bisección/Newton-Raphson)
ε = |xnuevo − xviejo|½·|xnuevo + xviejo| × 100
Exacto — absoluto
errorexacto = |xaprox − xexacto|
Exacto — porcentual
εexacto = |xaprox − xexacto||xexacto| × 100
La fórmula del "estimado" no es siempre la misma

El denominador de la versión porcentual del error estimado depende del enunciado — no hay una única fórmula universal. Ejemplos ya vistos en la materia:

  • Bisección/Newton-Raphson (parcial modelo): divide por el promedio de x_nuevo y x_viejo (fórmula (#) de arriba).
  • Jacobi/Gauss-Seidel (ver capítulo 2): divide por la norma del vector nuevo, E = ‖X_nuevo−X_viejo‖ / ‖X_nuevo‖ × 100.

Antes de programar el criterio de error, siempre conviene releer qué fórmula puntual pide ese enunciado — no asumir que es la misma del ejercicio anterior.

Ejemplo resuelto (Problema 1, parcial modelo)

f(x) = (x+1)/(x+4) − 0.25x, raíz exacta x=2 (punto a, despejado a mano). Bisección en [1.75, 3.2], última iteración (la 13ª): 

x_aprox (c)              = 2.0001037598
error estimado (#)       = 0.0088492470 %   (contra la iteracion anterior)
error absoluto exacto    = 0.0001037598     (contra x=2)
error porcentual exacto  = 0.0051880 %      (contra x=2)

Newton-Raphson desde x0=1.0, primera iteración:

x1                       = 2.1538461538
error estimado (#)       = 73.1707317073 %  (contra x0=1.0)
error absoluto exacto    = 0.1538461538     (contra x=2)
error porcentual exacto  = 7.6923076923 %   (contra x=2)
Por qué vale la pena calcular los dos

El error estimado es el único que existe en un problema real (nunca conocés la raíz exacta de antemano) — es la garantía práctica de que "ya convergió lo suficiente". El error exacto solo se puede calcular en ejercicios de práctica, y sirve para confirmar que el estimado no está mintiendo: en el ejemplo de Newton-Raphson de arriba, el error estimado (73%) es mucho más pesimista que el exacto (7.7%) en la primera iteración — son cantidades distintas, no hay por qué esperar que coincidan, sobre todo lejos de la raíz.

Ojo con qué pide cada enunciado, palabra por palabra

No todos los ejercicios piden las cuatro variantes. Leer con cuidado si dice "error", "error absoluto", "error porcentual" o "error exacto" a secas — cada palabra extra cambia cuál de las cuatro fórmulas de arriba corresponde. Si el enunciado dice "error exacto" sin la palabra "porcentual", es la versión absoluta (resta simple, sin dividir ni multiplicar por 100) — no asumir automáticamente que es un porcentaje.

Al calcular a mano: redondear recién al final, nunca en el medio

Si una cuenta a mano tiene varios pasos (por ejemplo, una iteración de Gauss-Seidel que usa x₁ recién calculado para obtener x₂), arrastrar un valor ya redondeado de un paso al siguiente contamina todo lo que viene después — el error final deja de reflejar el método y empieza a reflejar el redondeo intermedio.

Caso real: arrastrando x₂=4,26 (redondeado de 4,2667) en vez del valor completo, el error absoluto exacto de esa iteración dio 1,3552 en vez del 1,3597 correcto — una diferencia visible, solo por haber redondeado un paso antes de tiempo. Redondear únicamente al escribir la respuesta final, nunca durante la cuenta.

Transversal — errores recurrentes en C++

Cosas que se repitieron en más de un método, vale la pena tenerlas de checklist antes de entregar cualquier ejercicio:

  1. 1-indexado vs 0-indexado. El pseudocódigo de clase arranca los índices en 1; los arrays de C++ arrancan en 0. Revisar siempre el punto de arranque de cada loop (no solo el límite superior).
  2. &&, no ||, en la condición de corte. "Seguir iterando mientras no convergió y no me pasé del máximo de iteraciones" es una condición con &&. Con || el tope de iteraciones deja de funcionar como salvaguarda.
  3. Inicializar las variables de "valor anterior" (c_viejo, x_viejo) antes de usarlas por primera vez — si no, el primer error calculado es basura de memoria.
  4. Guardas de división por cero antes de dividir: el pivote en Gauss/Jacobi, la derivada en Newton, el denominador en secante.
  5. Guardar valores absolutos donde corresponde (fabs(...)) — comparar o acumular un valor con signo cuando la lógica pide magnitud es una fuente de bugs difícil de ver a simple vista.
  6. cout trunca a 6 cifras significativas por default — si la tolerancia es más estricta que eso (ej. tol=1e-12), el cálculo interno ya tiene esa precisión, pero no se ve en pantalla a menos que agregues #include <iomanip> y cout << fixed << setprecision(N) antes de imprimir. Ojo con el sentido inverso: si la tolerancia es floja (ej. 1e-5 o 1e-6), no forzar más decimales en el print — mostrarías dígitos que el cálculo no garantiza como correctos. La precisión que se imprime tiene que ser consistente con la tolerancia que realmente se usó para calcular, ni de más ni de menos.
  7. Un bug en una rama de código que nunca se ejecuta no se nota — el ejemplo real: el signo del determinante en Gauss estaba mal (faltaba compensar los swaps de fila del pivoteo), pero como ningún sistema anterior necesitaba pivotear de verdad, esa rama nunca corrió y el bug quedó escondido varios ejercicios. Se destapó recién con un caso que forzaba el pivoteo. Vale la pena, al probar un programa, buscar a propósito un caso que dispare cada rama del código (pivoteo, matriz singular, semilla que hace fallar el chequeo de derivada, etc.), no solo el caso fácil que "anda a la primera".
  8. Una lambda que usa otra lambda tiene que capturarla explícitamente. Si f es una lambda (auto f = [](double x){...};) y armás otra lambda que la usa adentro (por ejemplo, una derivada por diferencias finitas: auto df = [](double x){ return f(x+h)-f(x-h); };), el [] vacío de df no compila — hay que poner [f] (o [&]) para que df tenga acceso a f. Es fácil de pasar por alto porque en C++ normal (funciones sueltas, no lambdas) esto nunca hace falta.

Si tira un error de "sandbox" al abrir

Es un problema típico de las apps empaquetadas con Electron (como GeoGebra) cuando se corren sin ser dueño del sistema (exactamente el caso de una compu del lab, sin sudo): el archivo chrome-sandbox necesita permisos especiales de root para activarse, y sin eso GeoGebra puede negarse a arrancar. Es seguro para este uso — el sandbox de Electron protege contra código web malicioso, y acá no se está navegando ninguna página, solo usando la app localmente.
